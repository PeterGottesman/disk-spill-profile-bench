What spilled at SF1000

In the single-iteration Q9 trace, 187 placement transitions entered DISK: 118 from HOST (5.20 GiB of logical batch data) and 69 directly from GPU (17.53 GiB). These placements refer to 157 distinct physical batch IDs, whose deduplicated logical sizes total 21.52 GiB. There were 88 task preparations with DISK among their input tiers, showing that disk-resident data was read for later computation.

The GiB figures are logical batch sizes recorded by Quent, not bytes written to storage. Fan-out can create multiple placements for one physical batch; compression and temporary-file cleanup mean filesystem size is not a reliable spill-volume measure.

Separate SF1000 traces for Q1 and Q6 showed zero DISK placements at the same 1 GiB cap. Their warm times were 4.438 s and 2.089 s, respectively, versus 4.453 s and 2.092 s with 196 GiB. The large runtime difference was confined to Q9: 13.862 s at 1 GiB versus 7.076 s at 196 GiB, an additional 6.786 s.

Method and limits

Both timed runs used the same SF1/10/100/1000 Parquet inputs and three Q1/Q6/Q9 iterations per scale. Baseline run scaling_20260928T1353Z; capped run disk_scaling_1g_20260928. The NDJSON validation runs used Q9 once per scale and Q1/Q6 once at SF1000. A DISK placement is counted when a placement's memory-tier resource changes to DISK; its capacity_bytes supplies the logical size. DISK input tasks are Preparing events whose origin_tier contains DISK. Machine-readable measurements and session IDs.

With the tested inputs, the onset is between SF100 and SF1000 for Q9 at a 1 GiB host cap; intermediate factors were not available. The higher-capacity run had no DISK task mentions at SF1000. This is one machine and one memory configuration. Sirius printed thread-local-storage shutdown panics after completed queries; all expected timing rows and telemetry sessions were present.
